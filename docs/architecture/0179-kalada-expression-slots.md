# FormDefinition V1 Kalada expression slots (proposal, #179)

**Status: Owner-approved DESIGN, not implemented or executable.** The owner approves an in-place, greenfield V1 replacement of Kuery `ValueExpression<StateRef>` slots, with no legacy support, migration or converter requirement. Formbar engineering review remains necessary before [real FSX lowering (#184)](https://github.com/surikaterna/formbar/issues/184). Today's V1 runtime does not accept Kalada. See [schema compilation architecture](./schema-compilation.md) for the existing category boundaries.

## Baseline and decision boundary

At Formbar `origin/main` 3fcfcd0, `FormDefinition` has `{version: 1, id, root, computations?}`. `@formbar/declarative` is 0.22.1 and `@formbar/expressions` is 0.14.3 (package manifests). Validation copies finite safe JSON, compiles Kuery expressions, validates references and repeater scopes, and rejects duplicate computation IDs/targets, self-dependencies, and cycles. Runtime projects a captured form snapshot and evaluates via the Kuery service. Historically Kalada main's `@kalada/core` manifest was 0.5.0; that baseline is not a grammar limit for #184. Its generated [0.6.0 release PR #63](https://github.com/surikaterna/kalada/pull/63) is held pending coordinated RC go/no-go, not merged or a published dependency to assume. Internal #184 tests may use exact pinned, audited, locally packed current Kalada core/syntax/composition candidates (including supported `&&`); final Formbar release must depend on the matching *actually released* Kalada artifacts and verify their installed feature set and package graph. The owner wants one coordinated RC train, not atomic publication: publish Kalada first, verify registry artifacts/versions, then Formbar against those exact available versions; neither publication is authorized now. This design uses the public `KaladaV1Program` / `compileKaladaV1Program` contract.

**Owner-approved design choice:** keep `FormDefinition.version: 1` and replace *only* expression-bearing slots with a full Kalada canonical program envelope. A V1 document written by the old Kuery client is incompatible: reject old Kuery expression slots deterministically at the exact declaration path with actionable **RE-AUTHOR** guidance. Never reinterpret a Kuery `kind`/`op` tree as Kalada or silently keep a second engine. No legacy support, migration or converter is required. Version 1 alone does not imply compatibility with old Kuery definitions. Existing stored documents, API clients, type exports, schema-generated definitions, demos and runtime consumers need a coordinated breaking release.

## Slot inventory (exact declaration paths)

`node` means every node type; `props` exists only on field/action/output/custom nodes. Each expression slot holds a whole program, not a source string or an expression subtree.

| Path in V1 definition | Proposed kind / runtime result | Not an expression slot |
| --- | --- | --- |
| `computations[i].expression` | Program; finite safe JSON value for stored target | `computations[i].id` literal ID, `.target` structured binding |
| `root...node.visible`, `.disabled`, `.readOnly` | Program; strict boolean | `id`, `type`, `presentation`, labels/titles/descriptions, children/branch arrays |
| `root...field.required` | Program; strict boolean | field `binding` structured target, `widget` ID |
| `root...action.payload` | Program; finite safe JSON value, subject to action's payload rules | action `action` ID, `target` binding, `concurrency` literal |
| `root...output.value` | Program; finite safe JSON value | output `format`/`label` literals |
| `root...conditional.condition` | Program; strict boolean | `then` / `else` child arrays |
| `root...{field,action,output,custom}.props[name]` with `mode: "read"`: `.expression` | Program; finite safe JSON value | `mode: "literal"` `.value` stays JSON data; `mode: "write"` stays a *direct structured reference* (today shaped as `{kind:"ref",ref:StateRef}`), never an evaluated program. Write semantics are out of scope ([#180](https://github.com/surikaterna/formbar/issues/180)). |

`root...` includes descendants under group/section/repeater/custom `children`, conditional `then`/`else`, tabs `tabs[i].children` and accordion `items[i].children`. Repeater `binding`/`scope`/`minItems`/`maxItems`, validation `binding`/`messages`, and presentation attributes remain non-expression data. Preserve optional/required status and structural validation of each path. No whole-node or arbitrary attribute expression inference.

## Portable program and admission

Each slot stores exactly `{ "format": "kalada-program", "version": 1, "profile": "kalada-v1", "expression": <canonical Kalada V1 expression> }` (the Kalada public `KaladaV1Program` envelope). For example, a first-slice read-only FSX fixture with a boolean condition (`data.show`) and an output derived directly from an input field's `data.amount` (illustrative, subject to installed core admission):

```json
{
  "version": 1, "id": "sample",
  "root": { "type": "group", "id": "root", "children": [
    { "type": "conditional", "id": "gate",
      "condition": { "format": "kalada-program", "version": 1, "profile": "kalada-v1",
        "expression": { "kind": "ref", "ref": { "namespace": "data", "segments": ["show"] } } },
      "then": [ { "type": "output", "id": "total-display",
        "value": { "format": "kalada-program", "version": 1, "profile": "kalada-v1",
           "expression": { "kind": "ref", "ref": { "namespace": "data", "segments": ["amount"] } } } } ] }
  ] }
}
```

Here `data.amount` is input snapshot data, not a computation target. The first FSX slice evaluates conditions and outputs against a captured snapshot and renders the output only: no computed form-data mutation, computation scheduling/write-back, or hidden side effects. Any supplied `computations[i].expression` must already pass compile-time program/reference/scope/dependency and duplicate-ID/target/self/cycle validation in this slice, even though computation execution and target writes need a separate reviewed issue.

Admission does **not** evaluate this example: copy/validate safe finite JSON (no getters, cycles, prototypes, functions, sparse arrays, nonfinite numbers), check the exact envelope discriminator/version/profile and reject extra/unknown data, then call core `compileKaladaV1Program` with Formbar's reference codec and bounded limits. Compilation/validation of **any** expression slot, including supplied computations and dependency/graph and reference checks, must never invoke an evaluator, renderer or capability callback; it only checks static data and policy. Store the *canonical data program* returned by core, never a compiled closure, `WeakMap` key, linked host object or live snapshot. Reject malformed envelopes and unsupported core node forms/versions; do not invent an implicit translation or drop unknown keys. Prefix core diagnostic paths with the slot path (e.g. `root.children[0].condition.expression...`), retain a stable Formbar code and actionable reason; legacy `{kind:"literal"|"ref"|"op",...}` at the slot fails specifically at that declaration path with **RE-AUTHOR** guidance. `FormDefinition.version !== 1` remains unsupported. Internal tests admit only features in the exact pinned audited packed candidate; release admission must match the actually installed released `@kalada/core` version, rejecting mismatched/unsupported program versions or nodes rather than assuming candidate support exists in 0.5.0.

## References, graph and scope

Use core's public `KaladaV1ReferenceCodec` with a Formbar structured `StateRef` as JSON ref payload, **not** Kalada's default string refs: `{namespace: string, segments: (string | nonnegative safe integer)[], scope?: string}`. Exact keys, safe names (no prototype-polluting path segments), bounded path length, permitted namespaces and scoped/absolute shape are validated at declaration time. Do not treat a dotted string as a path. Restrict runtime reads to `data`, `ui`, `form`, `field`; `form` permits only one status key (`valid`, `validating`, `submitting`, `dirty`, `touched`, `submitted`), and `field` requires `[nodeId, key]` with key `valid`/`validating`/`dirty`/`touched`. Validate those shapes and field ID membership/context at the Formbar boundary, not as arbitrary Kalada evaluator semantics; do not grant namespace access based solely on syntax. `field` reads remain contextual to a concrete instance at use time; reject unresolvable field IDs rather than silently reading another instance. `data`/`ui` reads still require available snapshots and use-time authorization. Bindings/targets additionally retain their existing write/target namespace restrictions; read allowlisting never authorizes a write.

During tree validation, check every scoped dependency against **lexically enclosing** repeater scopes, with matching namespace and a resolvable parent chain. Top-level computations compile/validate with empty scopes: no scoped targets or scoped dependencies. Resolve relative references against concrete per-instance repeater bindings only at runtime; the stored canonical program and its static scope tokens stay index-free. No current array index or contextual field value is serialized into the program. Revalidate namespace availability, authorization and membership at use time after expansion (including removal/reordering); missing/denied is a diagnosed failure, not an empty/null/false value.

Use core's compiled **static** `dependencies` (including conditional branches), canonicalize each structured ref through Formbar's codec, normalize resolved absolute keys as `[namespace, segments]` (preserve segment types), deduplicate, and feed the existing computation-ID/target/self/cycle checks for **every supplied computation in the first slice**. Validate that graph before any computation evaluation, so a lazy branch cannot hide a cycle. For computations, compare absolute targets to absolute dependencies; for scoped node expressions keep lexical descriptors until each instance is resolved. An invalid/unknown scope or duplicate target is a definition error, not a runtime scheduling hint. The first FSX slice reads captured snapshots for conditions and outputs only; future computation execution, scheduling and target write-back require separate review. No compile-time evaluation.

## Results, diagnostics and ownership

Kalada core owns parsing-independent canonical AST semantics, static dependency discovery and evaluation diagnostics. Formbar owns definition admission, reference codec and capability policy, captured snapshot/resolver, repeater expansion, contextual `field` reference resolution, node/output/prop result gates and fallback; future computation scheduling stays outside the first FSX slice. The evaluator receives only an authorized resolver returning explicit `found`/`missing`/`denied` outcomes. Evaluation/reevaluation is permitted only later at use time under Formbar's authorized runtime resolver, never during compilation or definition validation. At use time, a strict boolean is required for visible/disabled/readOnly/required/condition: reject both `Option.some` and `Option.none` with a **typed** property/instance diagnostic, even when `some` contains a boolean; no unwrap, coercion or default except the existing fail-closed policy. On evaluation/type failure emit a property/instance diagnostic; use current fail-closed fallbacks (visible false, disabled/readOnly true, required true, conditional no branch). Absent optional slots keep existing defaults (visible true, disabled/readOnly false, required true). Output failures retain `error` status rather than a fabricated value; payload/read-prop/computation failures do not silently emit values or write targets. Review fallback behavior per consumer in implementation tests.

For JSON-valued slots accept only *finite, safe JSON* results after evaluation. The agreed boundary rejects both `Option.some` and `Option.none` with a **typed** property/instance diagnostic, as well as Result, temporal values, functions/closures and other non-JSON Kalada values, **even if** a wrapper contains a JSON primitive; no implicit unwrap, coercion, null substitution, omission, default or `undefined`. `null` is an explicit JSON value, distinct from missing and from `Option.none`. Any slot-specific conversion requires a later separately approved contract. Pure expressions that provably produce unsupported types may be rejected at admission where core exposes sufficient static evidence, without invoking callbacks; otherwise reject at evaluation with a typed diagnostic. No arbitrary JS, parser/editor/host dependency, or serialized execution capability enters the runtime.

Definition diagnostics use structural paths today. For [#184](https://github.com/surikaterna/formbar/issues/184), FSX source lowering should attach a separate mapping from definition slot/inner core diagnostic paths to original source UTF-16 ranges; missing mapping falls back to the definition path. Do not persist source maps or require syntax/editor packages for portable runtime admission. The future source adapter owns source ranges; core owns inner expression paths; Formbar combines them without pretending current JSON definitions have FSX ranges.

## Proposed acceptance matrix and implementation sequence

| Case | Expected future evidence (not currently passing) |
| --- | --- |
| First FSX slice: conditional `condition` and output `value` read boolean/primitive JSON from input snapshot | Validate program data, extract deps, evaluate against captured snapshot and render output without computation scheduling, target writes or side effects; sample above exercises condition + output. |
| First slice with supplied `computations[i].expression`; future field `visible`/`required` and read-only prop consumers | Compile and statically check every supplied computation's refs/scopes/dependencies and duplicate ID/target/self/cycles (including lazy branches) before any evaluation; spy evaluator/renderer/capability callbacks remain at zero during validation. No computation execution/write-back in the first slice. Later consumers preserve node/instance fallback behavior. Test supported `&&` condition on the exact pinned packed candidate when its syntax/core support is present; reject a candidate/installed-version mismatch and re-test against the actually installed released Kalada artifacts before Formbar RC publication. |
| Old Kuery literal/ref/op and wrong/missing format/version/profile, extra keys, non-JSON AST | Deterministic rejection at exact declaration slot path with actionable **RE-AUTHOR** guidance for old Kuery slots and invalid-program diagnostics for malformed programs; no converter fixtures. |
| Malformed structured ref, namespace/field key or unknown/out-of-lexical-scope repeater ref | Definition path failure; top-level computation rejects scopes, runtime checks authorization and concrete instance again. |
| Repeated dependencies, duplicate computation ID/target, self-edge, two-node cycle (including lazy branch) | Stable deduped graph keys; diagnosed duplicate/self/cycle before evaluation. |
| Missing or denied ref, non-boolean gate, non-JSON/Option result, numeric/type evaluator error | Property/instance diagnostic with fail-closed default or output error; no coercion, omission, write or hidden fallback. |
| Negative fixture: valid and invalid programs in every expression slot with spy evaluator, renderer and capability callbacks | Compilation/definition validation (including reference and graph checks) invokes each spy **zero times**; static diagnostics still appear. Runtime evaluation/reevaluation is separately tested only at use time under Formbar authorization. |
| Negative fixture: `Option.some(true)` and `Option.none` at a boolean gate; `Option.some(1)` and `Option.none` at a JSON-valued slot | Each variant gets a **typed** property/instance diagnostic; boolean gates use only existing fail-closed policy, JSON-valued slots never unwrap, coerce, default, omit or emit a value. |

1. **Admission/ref codec:** define portable slot types, exact envelope and JSON/codec checks; use exact pinned audited locally packed Kalada core/syntax/composition candidates for internal #184 tests, including `&&` only where supported. Test legacy rejects, unsupported nodes and version mismatch. No parser/editor dependency in runtime.
2. **Validator/graph:** replace Kuery slot validation; in the first slice compile and statically validate any supplied computations, lexical scopes, namespace/field references and normalized dependencies for duplicate ID/target/self/cycle checks without invoking evaluator, renderer or capability callbacks; update schema-generated definitions and public client contracts.
3. **First FSX runtime evaluation/fallback:** integrate core evaluation for conditions and outputs with Formbar's captured snapshot resolver and authorized namespaces; test failures and result gates without scheduling computations or writing computed form data. Defer other slot consumers and computation execution/write-back to separately reviewed implementation scope.
4. **Remaining slots/exports/release:** cover payload/read props and all public surfaces, consumer/build tests and explicit rejection/**RE-AUTHOR** guidance; no converter. Before Formbar RC publication, verify fresh installed released Kalada registry artifacts/versions and run packed ESM/CJS/NodeNext/browser/runtime consumer and version-mismatch rejection tests against the matching exact dependency versions. Keep Kalada PR #63 held until RC go/no-go; publish Kalada first, then Formbar, not atomically. Publishable incompatible packages require **major Changesets when implemented** and release-owner review; no Changeset for this docs-only design and no publication authorization here.

The [component registry design (#183)](https://github.com/surikaterna/formbar/issues/183) decides renderable component IDs/props separately. [Real FSX (#184)](https://github.com/surikaterna/formbar/issues/184) owns source lowering/range mapping; [writes (#180)](https://github.com/surikaterna/formbar/issues/180) owns repeated-item stable write semantics. None is implemented by this document. Formbar engineering must review the exact reference codec, scope rules, dependencies and graph validation, runtime behavior, installed released core capabilities/version and major release impact before implementation. The owner-approved greenfield V1 in-place envelope rejects old Kuery slots; `Option.none` omission is not an open product decision.
