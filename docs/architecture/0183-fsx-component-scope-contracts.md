# FSX component, scope and capability contracts (#183)

**Status: Draft / Proposed — needs design review, not approved or executable.** This is a CF04/CF05 fixture proposal, not passing conformance evidence. Formbar state/rules and Kalada architecture owners must review it independently before #184 implements source lowering. [#179's expression-slot proposal (PR #284)](https://github.com/surikaterna/formbar/pull/284) is open, not approved or implemented: the Kalada slot admission/lowering below is **conditional** on its approved contract, and must be revised if that contract changes. Coordinate [Kalada #107](https://github.com/surikaterna/kalada/issues/107) and [Formbar #92](https://github.com/surikaterna/formbar/issues/92)/[#93](https://github.com/surikaterna/formbar/issues/93); none is automatic signoff.

## Baseline and ownership

At Formbar `origin/main` **3fcfcd0**, `packages/declarative/src/definition.ts` declares `FormDefinition.version: 1` with required `id` and `root` and optional `computations`; `nodes.ts` has group/section/field/repeater/action/output/conditional/tabs/accordion/validation/custom, not an FSX Form node. `validators/nodes.ts` admits exact node keys, structured repeater scopes and branch/child arrays; `validators/bindings.ts` validates structured `{namespace,segments,scope?}` bindings. Today expression slots are Kuery, **not** Kalada programs. `validators/nodes.ts:nestedContext` rejects duplicate repeater scope IDs against one shared set, even across siblings. `packages/react-schema/src/extension-registry.ts` accepts host-provided widget/custom-node registrations with executable `validateProps`; that is a **renderer** boundary, not a source-installable FSX compiler registry. See [schema compilation architecture](./schema-compilation.md) for the distinct data-evidence/presentation/runtime categories.

**Proposed boundary:** a trusted host installs and versions a finite FSX compile profile (component descriptors, guest languages, capabilities, expected slot types, child rules and lowering targets). Pin profile ID/version for a compilation; reject unavailable/mismatched versions rather than reinterpret source under a changed registry. The source can *select* permitted identifiers and supply data, never define registrations, parser plugins, validators, callbacks or JavaScript. Host-owned renderer/action implementations are resolved separately under their own trust policy; selecting an ID grants no executable authority. Reject duplicate descriptor/attribute/capability IDs at host profile setup. Invalid authored content produces a source diagnostic and no executable definition, not a best-effort fallback. The registry is proposed design metadata, **not** a claim that a registry API already exists.

## Descriptor surface (not finalized source spelling)

Each installed descriptor declares: stable component ID and version/profile membership; lowering target and required/optional attrs; each attr's **kind** (static finite JSON literal, guest expression value, or direct structured location), expected result (`boolean` strict, safe finite `JSON`, or a specified Scheman-derived data type), permitted guest language IDs for expression attrs, and available capability IDs with their host-defined metadata/limits. It also declares legal ordered children/branches and whether a repeater introduces a lexical alias. Exact schemas/types and error messages are profile-versioned; no unknown attrs, children, capability names, or implicit type coercion. Resolve capabilities against both component and host profile; source cannot turn on a missing capability. A statically provable wrong expression type is a source error; otherwise runtime result gating must diagnose the mismatch, not coerce it. Scheman v2's recursive data-schema descriptors and `@formbar/from-schema`'s selected-side occurrence/evidence projection supply data facts (constraints, presence and types), **not** UI component/capability metadata, a universal shared checker or authorization to write. No hardcoded guest-fragment type is assumed; inspect the released guest's public composition contract before implementation.

| Illustrative component | Required slots and allowed children | Proposed lowering boundary |
| --- | --- | --- |
| Root Form | Static default guest language; declared root children only | Authoring-only wrapper; emits V1 `FormDefinition {version: 1, id, root: {type: "group", id, children}}`, not a new V1 node or runtime prop. |
| Conditional | Strict boolean expression condition; explicit then/optional else branches containing permitted nodes | V1 `conditional.condition`, `.then`, `.else`. |
| Field | Direct structured location, static widget ID; **no children** | V1 field `binding` and `widget`; widget/prop support requires installed capability. |
| Output | JSON-safe expression value; no children by default | V1 `output.value`; format is an installed/static option, not source code. |
| Repeater | Direct structured array location, unique alias; permitted child nodes | V1 repeater `binding`, `scope`, `children`; initially read-only FSX binding behavior. |
| Action | Static action ID; **no children**; V1 built-in payload/target rules apply | V1 action declaration is outside the first read-only FSX execution slice; no action invocation at parse, compile or expression evaluation time. Write/target authorization is deferred to #180/#185. |

The root wrapper must supply a stable, valid V1 definition `id` and a distinct root group `id` (for example, a documented reserved root-ID derivation from the Form ID); whether the source explicitly provides the Form ID or a deterministic source identity supplies it is a future source-design decision. Do not silently invent an ID from a mutable position or collide with authored/generated node IDs: reject missing/unavailable identity or any collision before emitting V1. The root `children` array is required, including when empty; compile-time guest selection is not serialized. A `section` root would also be valid if explicitly selected by a future profile, but is not implied by the wrapper.

Other V1 nodes and props need explicit descriptors before FSX can emit them; their presence in V1 does not make them valid FSX tags. In V1 `validators/nodes.ts`, field and action have no `children` key; exact-key validation rejects it. A host descriptor cannot override that restriction: a future nested source construct would need a separately specified, explicitly validated alternate V1 lowering, not a field/action with children. Attributes like labels/IDs and literal props remain static data; `visible`, `required`, `condition`, `value`, payload and read props are expressions **only where** their descriptor permits and #179 approves the corresponding V1 program slot. Direct locations (field/repeater binding, action target, write prop or computation target) are structured references, never evaluated expressions, even if the expression evaluates to a string/path. V1 binding segments are at most 64 safe nonempty strings (excluding `__proto__`, `constructor`, `prototype`) or non-negative safe integers; `namespace` is a safe identifier and a scope, if given, must resolve. A structurally valid binding still needs a namespace and target kind permitted by its slot/profile; do not claim V1 requires `data` for every binding. No `bind` keyword or tag/attribute spelling is selected here. `mode: "write"` semantics, mutations and stable item write identity belong to [#180](https://github.com/surikaterna/formbar/issues/180)/[#185](https://github.com/surikaterna/formbar/issues/185); [#175](https://github.com/surikaterna/formbar/issues/175) owns codecs. Neither schema evidence nor a renderer's `validateProps` callback becomes an FSX source language or universal shared checker.

For any later admitted V1 action, `validators/actions.ts` requires a payload expression for `array.append`, `array.insert`, `array.move` and `array.swap`; `array.remove` has no required payload. Payload is forbidden for `submit`, `reset` and `validate`. Only the five array actions accept a target, and each requires a structured binding with `namespace: "data"`; non-array actions reject targets. A host capability descriptor cannot relax these V1 invariants. These are declaration-validation rules, **not** permission for first-slice FSX action execution or a claim that #179 program payloads or #180 writes are available.

## Guest selection, aliases and source ownership

The first consumer proposes a **static compile-time default language on the root Form** (`Kalada`), inherited by eligible descendant expression slots. It is not an expression and never leaks into V1 props. The root has no separate document directive. If later needed, a trusted allowlist may permit a nested element default for its subtree and a per-expression override, with precedence override > nearest nested default > root default; adding those controls requires a versioned profile review, not a general configuration framework. For every slot resolve the *chosen* language and check that the profile/slot permits it. Unknown, ambiguous, absent or forbidden selections are diagnosed at the selecting source range (or slot if inherited), **never** silently replaced by Kalada or a unique allowed guest. Direct-location and static slots cannot carry guest selectors. Neither the default nor overrides can install guests.

Repeater aliases are explicit lexical identifiers tied to their enclosing repeater's structured binding, namespace and parent chain. Inside a nested repeater, both its alias and a distinct outer alias remain addressable; a sibling/outside alias is unresolved. Top-level computations have no enclosing aliases. Reject duplicate names at definition scope, **including siblings and shadowing**, consistent with today's global `duplicate-scope` validator; do not claim shadowing until a separately reviewed V1 scope change. Resolve reads against concrete instance paths at use time, after reorder/removal and authorization; static alias references carry no index as stable identity. Initial FSX repeaters are read-only: positional indexes must not become durable write addresses.

The FSX language owns the enclosing source AST and UTF-16 offset ranges. Only a host-installed guest parser consumes a bounded expression subtree through its **public composition interface**; Kalada owns its guest AST and lowering/semantics, not the Form tree. Source adapter maps guest-relative ranges to enclosing source offsets and keeps a transient mapping from source ranges to V1 declaration paths (including inner expression diagnostics); invalid ranges or failed guest lowering diagnose source, not guessed locations. Conditional on #179 approval, lower admitted Kalada guest programs into **Formbar V1 DECLARATIONS** for exactly the approved expression slots, validate resulting V1 structural/reference/capability rules, and hand runtime only portable program data. Formbar runtime owns dependency scheduling and authorized snapshot resolution, with no FSX/guest parser, source map, callback or JavaScript dependency. If a mapping is missing, show the declaration path only; never invent a source span. Pin the released Kalada public composition/core capabilities at implementation time rather than assuming unreleased features.

## Illustrative source intent and proposed fixtures (not syntax acceptance)

This indented sketch names concepts rather than final FSX tags, attribute spelling or a `bind` keyword:

```text
Form [defaultLanguage: Kalada]
  Repeater [location: data.orders, alias: order]
    Repeater [location: order.lines, alias: line]
      Conditional [condition: Kalada(line.show && order.enabled)]
        then: Output [value: Kalada(line.total)]
```

Read-only: `line` and distinct outer `order` resolve lexically; no source-supplied components or executable callbacks. The actual binding/guest syntax and runtime truth/result behavior require #179 and #184 decisions.

| Fixture input (proposed) | Expected future evidence, **not run** |
| --- | --- |
| Sketch above with installed profile and allowed condition/output capabilities | Resolve both aliases; lower boolean condition and JSON output to approved V1 program slots with mapped ranges; runtime reads snapshot only. |
| Unknown component/attr/capability, missing host-installed guest, forbidden selected default/override | Source-path diagnostic; reject, do not drop attr, fall back or register source content. |
| Field with children; wrong branch or expression result type; unknown widget/format | Reject at descriptor or V1 validation; runtime type failure if not statically decidable, with property/instance diagnostic. |
| Action with children; `array.append` without payload; `submit` with payload; `array.move` targeting `ui`, or `validate` with target | Reject at source/V1 validation; registry cannot waive V1 action or child-key rules. No first-slice action execution. |
| Root Form with missing/unstable identity or a root ID colliding with another node | Reject rather than silently minting a synthetic ID; valid root group requires `id` and `children`. |
| Duplicate alias (nested or sibling), unresolved/out-of-lexical alias | Reject at scope/source path; no silent shadowing or cross-instance read. |
| Source-provided registry/parser/validator/callback/JS or action invoked during compile | Reject source capability/execution request; host action stays deferred. |
| Computed expression in direct-location slot | Reject expression even if it returns a plausible path; slot requires structured location. |
| Structured location with malformed segment (e.g. `-1` or `"__proto__"`), unresolved scope, wrong namespace or wrong slot target kind (e.g. non-array field binding where profile requires an array, or `ui` for an array-action target) | Reject separately from computed-location diagnostics; validate structure/scope with V1 and slot-specific namespace/type with the trusted profile (array-action `data` also enforced by V1). Do not assume V1 checks every slot's data shape. |
| Stale repeater index reused for a write | No indexed write contract in this phase. |
