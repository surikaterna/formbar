# FSX component, scope and capability contracts (#183)

**Status: Owner-approved design direction; proposed contracts and fixtures, not engineering-approved or executable.** The owner approved #183's component/scope direction and [#179's in-place V1 Kalada slot direction (PR #284)](https://github.com/surikaterna/formbar/pull/284): greenfield Formbar replaces Kuery expression slots with portable Kalada programs, rejecting old Kuery shapes at exact declaration paths with re-author guidance; no legacy reads, dual engine, V2 converter or migration tooling. PR #284 remains open, with engineering/state-rules and Kalada architecture review and code implementation pending; current V1 does **not** support Kalada programs. This is a CF04/CF05 fixture proposal, not passing conformance evidence or authorization for [#184](https://github.com/surikaterna/formbar/issues/184) to implement source lowering before independent review. #184 is an internal read-only integration fixture; [#291](https://github.com/surikaterna/formbar/issues/291) is the implementation bridge for custom prop runtime support before the first **user-usable** milestone [#292](https://github.com/surikaterna/formbar/issues/292). Coordinate [Kalada #107](https://github.com/surikaterna/kalada/issues/107) and [Formbar #92](https://github.com/surikaterna/formbar/issues/92)/[#93](https://github.com/surikaterna/formbar/issues/93); none is automatic signoff.

## Baseline and ownership

At Formbar `origin/main` **3fcfcd0**, `packages/declarative/src/definition.ts` declares `FormDefinition.version: 1` with required `id` and `root` and optional `computations`; `nodes.ts` has group/section/field/repeater/action/output/conditional/tabs/accordion/validation/custom, not an FSX Form node. `validators/nodes.ts` admits exact node keys, structured repeater scopes and branch/child arrays; `validators/bindings.ts` validates structured `{namespace,segments,scope?}` bindings. Today expression slots are Kuery, **not** Kalada programs. `validators/nodes.ts:nestedContext` rejects duplicate repeater scope IDs against one shared set, even across siblings. `packages/react-schema/src/extension-registry.ts` accepts host-provided widget/custom-node registrations with executable `validateProps`; that is a **renderer** boundary, not a source-installable FSX compiler registry. Its `literalProps` rejects nonliteral props; current rendering does not support expression-valued custom props. #291 must intentionally update this boundary before #292; this document does **not** claim current support. See [schema compilation architecture](./schema-compilation.md) for the distinct data-evidence/presentation/runtime categories.

**Proposed boundary:** a trusted host installs and versions a finite FSX compile profile (component descriptors, guest languages, capabilities, expected slot types, child rules and lowering targets). Pin profile ID/version for a compilation; reject unavailable/mismatched versions rather than reinterpret source under a changed registry. The source can *select* permitted identifiers and supply data, never define registrations, parser plugins, validators, callbacks or JavaScript. Host-owned renderer/action implementations are resolved separately under their own trust policy; selecting an ID grants no executable authority. Reject duplicate descriptor/attribute/capability IDs at host profile setup. Invalid authored content produces a source diagnostic and no executable definition, not a best-effort fallback. The registry is proposed design metadata, **not** a claim that a registry API already exists.

## Descriptor surface (other tag/attribute spelling not finalized)

Each installed descriptor declares: stable component ID and version/profile membership; lowering target and required/optional attrs; each attr's **kind** (static finite JSON literal, guest expression value, or direct structured location), expected result (`boolean` strict, safe finite `JSON`, or a specified Scheman-derived data type), permitted guest language IDs for expression attrs, and available capability IDs with their host-defined metadata/limits. For CUSTOM, the trusted versioned descriptor specifies **per prop** literal, Kalada read expression, or direct writable structured StateRef with expected Scheman type; a computed expression is never a write target. It also declares legal ordered children/branches and whether a repeater introduces a lexical alias. Exact schemas/types and error messages are profile-versioned; no unknown attrs, children, capability names, or implicit type coercion. Resolve capabilities against both component and host profile; source cannot turn on a missing capability. A statically provable wrong expression type is a source error; otherwise runtime result gating must diagnose the mismatch, not coerce it. At boolean and JSON result gates, branded `Option.some` and `Option.none` are wrong types even if `some` contains an otherwise valid value: issue a typed diagnostic, never unwrap, omit, turn `none` into null, or otherwise silently convert. Explicit unwrapped JSON `null` is valid at a JSON gate, not at a boolean gate. Scheman v2's recursive data-schema descriptors and `@formbar/from-schema`'s selected-side occurrence/evidence projection supply data facts (constraints, presence and types), **not** UI component/capability metadata, a universal shared checker or authorization to write. No hardcoded guest-fragment type is assumed; inspect the pinned, reviewed local packed guest source-tooling composition contract during implementation, without assuming those artifacts are released.

| --- | --- | --- |

The first slice requires explicit, static `Form.id` as the stable V1 definition `id`. Derive a distinct group root ID deterministically, e.g. reserved `root:${Form.id}`. Validate both IDs against V1's safe identifier rules (nonempty, at most 256 characters, excluding unsafe names), including the derived ID's length, and reject any authored/generated node ID collision before emitting V1. Never truncate, silently mint an ID from a mutable position or accept missing identity. The root `children` array is required, including when empty; compile-time guest selection is not serialized. A `section` root would also be valid if explicitly selected by a future profile, but is not implied by the wrapper.

Other V1 nodes and props need explicit descriptors before FSX can emit them; their presence in V1 does not make them valid FSX tags. In V1 `validators/nodes.ts`, field and action have no `children` key; exact-key validation rejects it. A host descriptor cannot override that restriction: a future nested source construct would need a separately specified, explicitly validated alternate V1 lowering, not a field/action with children. Attributes like labels/IDs remain static data; `visible`, `required`, `condition`, `value`, payload and custom read props are expressions **only where** their descriptor permits and the corresponding #179 in-place V1 Kalada program slot has been engineered and reviewed. Owner approval of #179's direction is not current V1 support or engineering signoff. In this slice `Field.value` is specifically a direct location and `Output.value` specifically a Kalada expression; exact source punctuation remains subject to grammar review. Direct locations (field/repeater binding, action target, custom write prop or computation target) are structured references, never evaluated expressions, even if the expression evaluates to a string/path. V1 binding segments are at most 64 safe nonempty strings (excluding `__proto__`, `constructor`, `prototype`) or non-negative safe integers; `namespace` is a safe identifier and a scope, if given, must resolve. A structurally valid binding still needs a namespace and target kind permitted by its slot/profile; do not claim V1 requires `data` for every binding. Repeater `mode: "write"` semantics, mutations and stable item write identity belong to [#180](https://github.com/surikaterna/formbar/issues/180)/[#185](https://github.com/surikaterna/formbar/issues/185); [#175](https://github.com/surikaterna/formbar/issues/175) owns codecs. Neither schema evidence nor a renderer's `validateProps` callback becomes an FSX source language or universal shared checker.

The **internal #184 read-only fixture** may lower a CUSTOM with typed literal JSON props and explicitly allowed children to a V1 `custom` node. This does not satisfy **first user-usable #292**: its trusted, versioned compile descriptor must admit separately typed literal, computed Kalada **read**, and simple direct **write** props, with an expected Scheman type per prop. Compile-time checking uses descriptor metadata without evaluating reads, executing writes or invoking source-supplied validators. The host independently installs the react-schema runtime renderer (and any trusted `validateProps`); missing renderer, invalid props or missing capabilities must diagnose/reject, not fall back. Source cannot install the descriptor, renderer, handler or callback. #291 must intentionally change `extension-registry.ts:literalProps`'s current nonliteral rejection and build the projection/setter bridge before #292; #184 is not silently expanded to implement it.

At use time, Formbar declarative evaluates each admitted read program reactively against authorized current form data, checks its expected result type and projects the value into props for the host-installed renderer; a data change must refresh the projection. A direct write prop is a structured StateRef to a nonrepeat target with the declared Scheman type, **not** an expression evaluating to a path. It exposes a separate **EPHEMERAL** guarded setter channel to the renderer, never serialized into JSON `ExtensionProps` and never a JS handler in FSX. The setter goes through core set-value, with use-time checks of current authorization, target resolution, revision, disabled/readOnly state and both client and server policy. Retain callbacks only while their instance/capability is valid; removal, replacement, authorization change or stale revision invalidates old callbacks, which must fail closed even if held by a renderer. No compile-time execution or ambient renderer write authority. #291 owns bridge implementation; #292 must prove this behavior before calling FSX user-usable. Simple direct nonrepeat set-value is the limit: inverse codecs stay with [#175](https://github.com/surikaterna/formbar/issues/175), independent nonrepeat server-authorized write proof with [#195](https://github.com/surikaterna/formbar/issues/195), and repeater writes with [#180](https://github.com/surikaterna/formbar/issues/180)/[#185](https://github.com/surikaterna/formbar/issues/185). Neither a permitted descriptor nor a passing read grants write authorization.

For any later admitted V1 action, `validators/actions.ts` requires a payload expression for `array.append`, `array.insert`, `array.move` and `array.swap`; `array.remove` has no required payload. Payload is forbidden for `submit`, `reset` and `validate`. Only the five array actions accept a target, and each requires a structured binding with `namespace: "data"`; non-array actions reject targets. A host capability descriptor cannot relax these V1 invariants. These are declaration-validation rules, **not** permission for first-slice FSX action execution or a claim that #179 program payloads or #180 writes are available.

## Guest selection, aliases and source ownership

The first #184 milestone is **FSX-host/Kalada-guest only**. Reverse Kalada Expressions-hosted FSX grammar ([Kalada #153](https://github.com/surikaterna/kalada/issues/153)) belongs to a separate later profile; it remains deferred, not a prerequisite for #184 or evidence of first-slice conformance. The first consumer requires **static compile-time `Form.defaultLanguage: Kalada`**, inherited by eligible descendant expression slots. It is not an expression and never leaks into V1 props. The root has no separate document directive. If later needed, a trusted allowlist may permit a nested element default for its subtree and a per-expression override, with precedence override > nearest nested default > root default; adding those controls requires a versioned profile review, not a general configuration framework. For every slot resolve the *chosen* language and check that the profile/slot permits it. Unknown, ambiguous, absent or forbidden selections are diagnosed at the selecting source range (or slot if inherited), **never** silently replaced by Kalada or a unique allowed guest. Direct-location and static slots cannot carry guest selectors. Neither the default nor overrides can install guests.

Repeater aliases are explicit lexical identifiers tied to their enclosing repeater's structured binding, namespace and parent chain. Inside a nested repeater, both its alias and a distinct outer alias remain addressable; a sibling/outside alias is unresolved. Top-level computations have no enclosing aliases. Reject duplicate names at definition scope, **including siblings and shadowing**, consistent with today's global `duplicate-scope` validator; do not claim shadowing until a separately reviewed V1 scope change. Resolve reads against concrete instance paths at use time, after reorder/removal and authorization; static alias references carry no index as stable identity. Initial FSX repeaters are read-only: positional indexes must not become durable write addresses.

The FSX language owns the enclosing source AST and UTF-16 offset ranges. Only a host-installed guest parser consumes a bounded expression subtree through its **reviewed composition interface**; Kalada owns its guest AST and lowering/semantics, not the Form tree. Source adapter maps guest-relative ranges to enclosing source offsets and keeps a transient mapping from source ranges to V1 declaration paths (including inner expression diagnostics); invalid ranges or failed guest lowering diagnose source, not guessed locations. Under #179's owner-approved in-place V1 direction, #184 lowers admitted Kalada guest programs into **Formbar V1 DECLARATIONS** for exactly the reviewed expression slots, validates resulting V1 structural/reference/capability rules, and hands runtime only portable program data; if this cannot fit #184, explicitly assign a preceding implementation issue rather than requiring completed #179 implementation before #184. Current V1 accepts Kuery slots, not Kalada programs; implementation must reject old Kuery-shaped declarations at exact declaration paths with re-author guidance, never silently convert them. Formbar runtime owns dependency scheduling and authorized snapshot resolution, with no FSX/guest parser, source map, callback or JavaScript dependency. If a mapping is missing, show the declaration path only; never invent a source span. For compiler source tooling pin and review local packed Kalada artifacts; for portable runtime admission use RELEASED `@kalada/core` (currently 0.5), and verify required canonical node features against that release at implementation time. Kalada PR #63 remains held; do not assume unreleased runtime features or require a released guest syntax/composition package before #184.

## Illustrative source intent and proposed fixtures (not syntax acceptance)

This indented sketch uses the approved explicit `as` repeater alias spelling for the first profile; other tag/attribute spelling and punctuation remain subject to grammar review:

```text
Form [id: "orders-form", defaultLanguage: Kalada]
  Repeater [location: data.orders] as order
    Repeater [location: order.lines] as line
      Conditional [condition: Kalada(line.show && order.enabled)]
        then: Field [value: line.total, widget: "text"]
        else: Output [value: Kalada(line.total)]
  CUSTOM [renderer: "trusted.summary", props: {tone: "quiet"}]
    Output [value: Kalada(data.summary)]
```

For the #184 read-only fixture, explicit `as line` and distinct outer `as order` resolve lexically without shadowing; `Field.value` is a location, `Output.value` an expression. CUSTOM needs separately installed compile descriptor and runtime renderer; its props here are literals. Actual binding/guest syntax and runtime truth/result behavior still need #179 engineering review and #184 implementation under the owner-approved V1 direction. #292 additionally requires the separate #291 custom read/write bridge and independent [#195](https://github.com/surikaterna/formbar/issues/195) nonrepeat write authorization proof, not inferred from this sketch.
